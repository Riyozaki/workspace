# Что этот маленький прототип проверяет — и чего не доказывает

## Разделение трёх вещей

1. **Языковое ядро:** неизменённая предобученная SmolLM2-135M-Instruct Q4_1.
   Это доступный контроль для инженерного запуска, не выбор лучшей существующей
   SLM и не новая архитектура AIra. Русский/факты/формат пока явно ненадёжны.
2. **Экспериментальная модель:** обученный здесь intent-router: линейный контроль
   и MLP с двумя применениями общей матрицы. Это не языковая модель.
3. **Система:** UI, ограничение вычислений, реальные инструменты, контур учительских
   исправлений и не-регрессионная проверка перед заменой весов.

Нельзя приписывать результат калькулятора языковому ядру, считать классификатор
новой LLM или считать успешный запуск маленьких весов доказательством будущего
качества сильного агента. Гипотеза о масштабировании остаётся открытой.

## Расчёты памяти — не измеренные ограничения качества

**РАССЧИТАНО:** при одинаковых четырёх битах на каждый параметр нижний payload:

| Параметров | Сырые веса, decimal GB |
|---:|---:|
| 135M | 0.0675 |
| 0.5B | 0.25 |
| 1.5B | 0.75 |
| 3B | 1.50 |
| 27B | 13.50 |

Это не RSS и не размер настоящего GGUF: есть scales, metadata, неравномерная
разрядность тензоров, embeddings, KV/cache, рабочие буферы и сам runtime.
**ИЗМЕРЕНО:** используемый Q4_1 файл —98,362,432bytes; веб-процесс при реальных
пробах около207MiB RSS. Из этой таблицы не следует качество больших вариантов.

Для обычного attention KV-кэш оценивается как
`2 * layers * kv_heads * head_dim * context_tokens * bytes_per_KV_element`.
При GQA и гибридных/SSM-архитектурах цена отличается. Уменьшение KV не устраняет
цену весов и не означает сохранения работы с длинным контекстом. Наш контекст1024
намеренно ограничен; это не сравнение с 8k/128k моделью при равном качестве.

Для batch1 dense decode **ПРЕДПОЛОЖЕНО** memory-bound приближение
`tokens/s <= effective_BW / weight_bytes_read_per_token`. Это не универсальный
предел всех архитектур: batching/speculation/cache меняют reuse, а compute и KV
могут стать другим bottleneck. Ватты и джоули в этой среде не измерены.

## Почему две петли не означают двукратное сжатие

У линейного контроля1539 параметров. У loop-router12987:
`512*24 + 24 + 24*24 + 24 + 24*3 + 3`.
Общая recurrent matrix24x24 применяется дважды. Если сделать две независимые
такие матрицы, добавится576 weights, а не удвоятся все12987. **РАССЧИТАНО:**
экономия против этой конкретной untied замены всего около4.2% полного числа
weights. В эксперименте loop вообще больше линейного контроля и проигрывает ему
на отложенных формулировках. Это не подтверждение архитектурного преимущества.

## AI Babysit: наблюдение, а не обещание самоулучшения

В реальном browser/API запуске исправление учителя перевело кандидатный прогноз
нового УЧЕБНОГО примера chat→notes. Но development accuracy упала80.56→72.22%.
Это не независимый тест и не доказательство полезного обучения. Внедрённый после
наблюдения guard не принимает кандидата с ухудшением dev accuracy/macro-F1 или
ростом числа ошибочных быстрых действий. Исходная регрессия сохранена, не удалена.

Проход dev-guard тоже не доказывает generalization: этот набор многократно
используется при разработке. Независимый holdout будущей языковой модели надо
отделить по семействам/источникам ДО авторства большого teacher-корпуса.

16 seed SFT-примеров в JSONL — формат и небольшой материал для ревью, не датасет,
который уже даёт высокое качество. Для8 примеров арифметика/JSON проверяются кодом;
остальные явно помечены как требующие ручного/независимого review. Веса SmolLM2
этим seed не обучались. Свободный текст учителя не даёт доступа к полным логитам
для KL-distillation; response-only SFT является отдельным практическим путём.

## Что должно предшествовать Kaggle-обучению

1. Реальные пользовательские RU/EN сценарии, лимит RAM/latency и минимальное железо;
   замороженный eval, не совпадающий с teacher-training families.
2. Доступный официальный unquantized pretrained donor/tokenizer с pinned revision;
   прогон сильного CPU runtime на той же задаче до изменений. Текущий135M выбран
   из-за доступности артефакта в этой среде, не как прогноз лучшего будущего ядра.
3. Проверки реального gradient path при frozen donor и prefix causality. Найденные
   ранее статическим чтением old donor/slow-pooling пути не объявлены исправленными:
   этот прототип их не импортирует и не выдаёт NumPy-router тесты за их проверку.
4. Обычный teacher SFT control против Babysit при учёте бюджета токенов, а не
   только числа примеров. После этого — одна архитектурная переменная за раз.
5. Возвращаемый checkpoint/adapter, реальный CPU-инференс, регрессии, peak RAM,
   first-content latency, task success и стоимость успешной задачи.

На этом этапе полного Kaggle language-model trainer и результатов такого обучения
НЕТ. Этот прототип проверяет локальный инференс и маленький feedback-контур;
подменять ими новую качественную универсальную архитектуру нельзя.
